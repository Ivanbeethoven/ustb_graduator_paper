
\chapter{背景介绍}\label{chap:background}
本章介绍相关概念与技术，并梳理 Kubernetes 权限提升漏洞相关的国内外研究现状。

\section{相关概念与技术}

\subsection{容器}
计算服务的部署形态经历了从物理机、虚拟机到容器化的持续演进过程（见图~\ref{fig:container-evolution}）。虚拟机部署依赖 KVM 等虚拟化技术，能够提供完整操作系统级别的隔离，但也带来了较高的虚拟化开销、较长的启动时间和较大的镜像体积，从而影响应用交付效率与资源利用率。相比之下，容器通过操作系统内核级的资源隔离共享宿主机内核，在资源利用率和启动速度上更具优势。容器以\textbf{镜像}为交付单元，将应用及其运行依赖整体打包。其实现主要依赖以下三类内核机制：
\begin{figure}[htb]
    \centering
    \includegraphics[width=0.9\linewidth]{images/容器.png}
    \bicaption{服务部署形式演进}{Evolution of service deployment paradigms}\label{fig:container-evolution}
\end{figure}

\begin{itemize}
    \item \textbf{命名空间（Namespace）隔离}：通过隔离进程、网络、挂载点等，使容器内运行的程序有独立系统抽象资源；
    \item \textbf{控制组（Cgroup）限制}：负责对容器施加 CPU、内存等硬件资源使用的强制规划，提供物理资源隔离；
    \item \textbf{只读分层与隔离挂载}：利用 OverlayFS 等联合文件系统\cite{wright2006versatility}，通过复用底层只读镜像并叠加独立的顶层读写区域，实现容器文件系统隔离。
\end{itemize}


\subsection{容器集群系统Kubernetes}
Kubernetes 是面向容器集群负载的分布式编排系统，简称 K8S。它源自谷歌内部的集群编排系统 Borg\cite{Verma_2015}，并于 2014 年正式开源。其核心思想是以\textbf{声明式 API}描述系统期望状态，再由控制平面持续驱动集群向该状态收敛\cite{kubernetes2024}。图\ref{fig:k8s-arch}展示了 Kubernetes 的基本体系结构。一个 Kubernetes 集群由\textbf{控制平面}和多个\textbf{工作节点}构成。控制平面负责集群控制、调度与状态协调，其中：\textbf{API Server}是资源访问与状态变更的统一入口，并结合键值数据库 ETCD 完成认证、授权、准入和资源对象持久化；\textbf{调度器}根据资源请求、亲和性与反亲和性等约束为工作负载选择节点；\textbf{控制器}负责持续调节各类资源状态，使其向期望状态收敛。工作节点侧，\textbf{kubelet}负责与 API Server 通信并维护本节点工作负载运行，\textbf{容器运行时}负责镜像拉取、容器创建和生命周期管理，\textbf{kube-proxy}负责服务转发与网络规则实现。
\begin{figure}[htb]
    \centering
    \includegraphics[width=0.8\textwidth]{images/k8s.png}
    \bicaption{Kubernetes 体系结构示意}{Overview of Kubernetes architecture}\label{fig:k8s-arch}
\end{figure}

Kubernetes 通过一系列持久化\textbf{资源对象}描述集群中不同资源的编排与管理。例如，\textbf{Pod}是最小调度单元，包含一个或多个共享网络与存储的容器；Deployment、StatefulSet 与 DaemonSet 分别面向无状态、有状态和节点守护型工作负载提供副本控制与更新策略；Service 与 Endpoint/EndpointSlice 提供稳定的服务发现与负载均衡抽象；Ingress 面向南北向流量提供入口控制；ConfigMap 与 Secret 用于配置和敏感信息的声明式注入；Volume、PV 与 PVC 则提供存储生命周期与绑定关系的抽象。


\subsection{Kubernetes 权限模型}
基于角色的访问控制（$\mathrm{RBAC}$）是 $\mathrm{Kubernetes}$ 授权机制的核心\cite{kubernetes2024}。图~\ref{fig:k8s-rbac-yaml} 左侧展示了权限元模型的形式化表达。该模型可以概括为\textbf{主语、动作与对象}之间的授权关系，即界定何种实体被允许对何种资源执行何种操作，其中：
\begin{itemize}
    \item \textbf{服务账户（ServiceAccount）}对应模型中的主语节点，表示发起请求的身份载体。在 Kubernetes 中，工作负载通常通过 ServiceAccount 与控制平面交互。
    \item \textbf{权限角色（Role/ClusterRole）}对应模型中的动作与对象约束，用于声明在特定作用域内针对各类资源（$\mathrm{resources}$）允许执行的操作动词（$\mathrm{verbs}$）集合。
    \item \textbf{角色绑定（RoleBinding/ClusterRoleBinding）}负责建立服务账户与权限角色之间的关联关系，从而完成授权。
\end{itemize}

图~\ref{fig:k8s-rbac-yaml} 右侧给出了一个典型的 $\mathrm{RBAC}$ 授权流程示例：首先创建名为 $\mathrm{kada}$ 的 $\mathrm{ServiceAccount}$；随后定义名为 \texttt{basic-operation} 的 $\mathrm{Role}$，并在其 $\mathrm{rules}$ 字段中授予对 $\mathrm{pods}$ 与 $\mathrm{secrets}$ 的 $\mathrm{get}$、$\mathrm{list}$、$\mathrm{create}$ 权限；最后通过 $\mathrm{RoleBinding}$ 将该 $\mathrm{Role}$ 绑定至 $\mathrm{kada}$ 账户。这类配置在接入第三方应用时较为常见，但若授予的权限范围超出实际需要，就可能引发权限提升风险。

\subsection{Kubernetes 权限提升漏洞}

权限提升是指攻击者在仅具备受限权限或初始执行能力的情况下，借助漏洞或错误配置将自身权限提升到更高等级的过程\cite{mead2003computer}。在 Kubernetes 场景下，这类问题既可能表现为授权范围扩大或横向获取，也可能表现为节点侧系统权限提升，从而影响更大范围的资源与工作负载。

在云原生环境中，权限提升的危害通常具有更强的放大效应。一方面，单个节点往往承载多个 Pod，一旦节点侧权限提升成功，攻击者便可能对同节点上的多个工作负载实施敏感信息窃取、运行环境篡改或恶意组件注入。另一方面，Kubernetes 的资源对象与运维动作高度集中且自动化，控制平面授权不当也会显著放大攻击后果。结合图~\ref{fig:k8s-rbac-yaml}中的示例，若主体被授予针对 $\texttt{Secret}$ 的 $\mathrm{get}/\mathrm{list}$ 权限，攻击者即可读取服务账户令牌、数据库口令或 API 密钥等敏感信息；若被授予针对 $\texttt{Pod}$ 的 $\mathrm{create}$ 权限，则可能进一步创建携带恶意镜像、特权配置或宿主机挂载的工作负载，作为横向移动、凭据窃取乃至后续节点侧利用的跳板。

图\ref{fig:cve-2024-33522} 以 \texttt{CVE-2024-33522} 为例展示了典型的节点侧权限提升漏洞。该漏洞源于 Calico CNI 安装程序的 SUID 位配置不当。若攻击者借助弱口令或服务暴露等前置手段获取节点本地访问权限，便可注入恶意二进制文件，并诱导安装程序以高权限执行。越权成功后，攻击者可以直接接管容器运行时数据、窃取高权限凭据并干扰网络组件，其影响将突破单一工作负载的隔离边界，迅速蔓延至整个集群。

\subsection{云原生安全技术}

云原生安全技术围绕镜像构建、资源准入、网络通信和运行时行为等关键环节形成分层防线，常见工具大多以规则化策略或声明式配置为载体，用于在不同阶段识别或约束风险。从作用位置看，这类技术大致可归纳为静态扫描与配置审计、准入控制、网络隔离和运行时监控四类，它们共同构成 Kubernetes 集群全生命周期安全治理的基础能力。

静态扫描与配置审计主要用于在镜像构建与部署前发现已知漏洞、弱配置和权限异常。代表性工具包括 Trivy\cite{trivy2025}、Grype/Anchore\cite{grype2025} 等镜像与依赖漏洞扫描工具，Syft\cite{syft2025} 等 SBOM 生成工具，以及 Kubescape\cite{kubescape2025}、kube-linter\cite{kubelinter2025}、kube-score\cite{kubescore2025}、KubeSec\cite{kubesec2025}、Polaris\cite{polaris2025}、Checkov\cite{checkov2025}、KubiScan\cite{kubiscan2024}、Krane\cite{krane2024} 和 RBAC Police\cite{paloalto2024} 等面向清单、IaC 与 RBAC 的审计工具。这类方法便于集成到 CI/CD 流程中，能够提前暴露高风险对象，但其判断依据主要来自既有漏洞库、配置基线和审计规则，对特定漏洞的真实利用条件仍缺乏上下文感知能力。

与之相比，准入控制、网络隔离与运行时监控更侧重集群运行阶段的风险约束。OPA/Gatekeeper\cite{opa2025} 与 Kyverno\cite{kyverno2025} 在 API Server 持久化资源前执行策略校验，可用于拦截特权容器、危险挂载和敏感权限变更；NetworkPolicy 及其在 Calico、Cilium 和 Weave Net 等插件中的实现，用于收敛服务间连通范围并降低横向移动风险；Falco\cite{falco2025} 则依托 eBPF 技术\cite{hoiland2018express}采集系统调用和 Kubernetes 事件，并通过规则引擎对异常行为进行实时检测与告警。这些技术分别从事前阻断、横向隔离和事中观测三个层面增强了集群安全性，但整体上仍以通用规则为主，难以直接围绕某一具体漏洞在补丁窗口期快速生成兼顾针对性与可部署性的临时防控策略。

\section{国内外研究现状}

本文面向云原生应用权限提升漏洞的智能化防控问题展开研究，其直接相关的研究基础主要来自三个方向：一是围绕权限提升风险形成机制与防控方法的通用研究，二是针对云原生场景中权限安全问题的分析与治理研究，三是大语言模型与多智能体驱动的智能化漏洞防控研究。基于这一问题链，本节依次梳理上述三个方向的代表性工作，归纳其主要进展与局限，并结合课题组前期研究说明本文的研究定位与切入点。

\subsection{权限提升风险与防控}

权限提升风险防护的基本原则是最小化权限原则。Saltzer 与 Schroeder 将最小化权限原则描述为：\textbf{每个程序与每个用户均应仅在完成任务所必需的最小权限范围内运行}\cite{saltzer1975protection}。早期研究通过权限范围形式化描述与管理防止权限提升风险。Ferraiolo 等\cite{ferraiolo1995role}提出基于角色的访问控制模型（RBAC），通过角色组织权限并建立主体与权限之间的间接映射关系，缓解了大规模系统中直接授权带来的管理复杂性。此后，Sandhu 等\cite{sandhu1999arbac97}进一步提出 ARBAC97 模型，将角色管理与授权管理纳入统一框架，表明权限安全研究不仅关注权限赋予本身，也关注角色传播与管理权限所引入的间接风险。Ferraiolo 等\cite{ferraiolo1999intranet}进一步给出了企业内网环境下 RBAC 的参考实现，说明相关研究已较早进入通用信息系统与组织级应用场景。除基于角色的权限组织方式外，Hu 等\cite{hu2014guide}系统总结了基于属性的访问控制（ABAC）思想，强调依据主体、客体、环境等多维属性动态决定访问授权，从而提升权限控制在复杂开放环境中的细粒度表达能力。总体而言，RBAC 与 ABAC 分别从角色抽象和属性约束两个角度，为最小权限原则在实际系统中的落地提供了基本的权限管理框架。

在既有权限管理框架基础上，研究进一步从系统结构和权限收缩角度探索权限提升风险的抑制机制。Provos 等\cite{provos2003preventing}提出特权分离方法，将操作系统服务划分为不同权限级别的组件并将高权限代码压缩到可信基范围内，从而为非特权应用最小化特权使用范围；Watson 等\cite{watson2015cheri}则通过对指令集架构、编译器及操作系统进行扩展，以支持细粒度的、基于能力的内存保护机制。这表明，权限提升防控并非仅依赖访问控制规则本身，也可以通过功能分解与权限隔离减少高权限执行路径。与此同时，角色建模与结构隔离均不足以彻底消除权限提升风险，冗余权限与过度授权在实际系统中仍普遍存在\cite{o1995redundant}。针对这一问题，后续研究依据日志等应用真实行为，结合规则和机器学习技术逆向推导应用所需的最小权限集\cite{molloy2012generative,sanders2018minimizing}。权限提升风险防控由权限分配问题扩展到授权管理、结构隔离和权限收缩。

软件系统组件化与平台化使得权限提升问题不再主要表现为单一主体对受限资源的直接越权，而更多体现为跨组件、跨应用的调用链滥用。Android 场景中的相关研究较早系统揭示了这一特点。Davi 等\cite{davi2010privilege}提出混淆代理攻击模型，指出低权限应用可通过伪造合法请求诱导高权限组件执行敏感操作，从而形成间接权限提升。Hutchinson 等\cite{hutchinson2018survey}进一步将此类问题概括为三个关键条件，即请求敏感权限、开放导出组件以及存在通向敏感 API 的执行路径。在此基础上，Bugiel 等\cite{Bugiel2012TowardsTP}指出，Android 多个应用进行协同共谋权限提升攻击；并提出一种面向系统的策略驱动运行时监控框架，从中间件与内核多个层面联合约束应用间通信与资源访问。上述研究表明，在复杂软件生态中，权限提升往往并非源于单点授权错误，而是沿调用关系、组件边界与信任链条逐级传播的结果。因此，权限提升风险的防控也需要由面向单点权限检查的静态约束，扩展到面向系统交互路径的联合分析与协同控制。

围绕权限提升风险的检测与防控分为静态架构分析、动态行为监控和数据流追踪三类。静态分析主要关注权限配置与应用组件的最小权限集是否匹配，例如 PScout\cite{au2012pscout}通过源码分析构建代码调用到权限检查点之间的可达路径从而检测过度权限，DelDroid\cite{bagheri2019deldroid}通过静态分析权限范围并推导最小权限集，SecComp\cite{wu2016seccomp}则在组件调用层面对非授权操作施加约束，以防御组件劫持引发的权限提升。动态行为监控侧重于运行时提权行为的自动识别，Sharmeen 等\cite{sharmeen2020adaptive}结合深度学习与半监督学习方法对权限提升行为进行检测，表明相关方法正由静态授权关系检查转向对真实运行过程的动态观测。数据流追踪通过污点分析技术关注敏感资源如何传播而导致的可能权限提升。Tripp 等\cite{tripp2009taj}提出面向 Web 应用的混合污点分析框架 TAJ，TaintDroid\cite{enck2014taintdroid}与 TaintMan\cite{you2017taintman}则分别在 Android 虚拟化环境和非 Root 真机环境中实现了对显式及部分隐式信息流的动态跟踪。总体而言，权限提升风险防控需考虑对静态代码、越权路径、运行行为和敏感数据传播。

总体而言，围绕权限提升风险已有研究已形成从权限约束到行为监控、再到信息流追踪的较完整分析路径。但相关工作主要针对移动应用、企业信息系统与Web系统，尚难直接回答云原生权限提升漏洞的识别与防控问题。

\subsection{云原生应用权限安全}

云原生权限安全研究的核心问题，不是单点配置是否合规，而是配置声明、控制平面授权、网络策略与运行时隔离如何共同影响权限风险的形成与扩散。由于 Kubernetes 将部署模板、控制平面接口、工作负载生命周期和节点侧运行环境耦合在同一编排体系之中，权限风险往往会沿配置、授权链路和组件交互同步传播。基于这一特点，现有研究大体可归纳为配置风险识别、模板与基础设施即代码安全分析、架构与授权链风险挖掘以及网络与运行时防护四类。

配置风险识别是云原生权限安全研究最早展开的方向，其研究重点也在逐步由合规性判断转向可利用性评估。早期工作主要用于勾勒 Kubernetes 配置安全的整体图景。Islam Shamim 等\cite{Islam_Shamim_2020}系统总结了 Kubernetes 安全实践，Shamim\cite{Shamim_2021}进一步指出部署清单偏离最佳实践可能直接演化为可利用的提权路径，Curtis 与 Eisty\cite{Curtis_2025}基于 Stack Overflow 数据的实证分析也表明配置安全始终是开发侧的核心关切。在此基础上，Rahman 等\cite{k8smanifests2023}对开源清单中的典型安全误配置进行了大规模归纳与实证研究。不过，静态扫描虽然能够发现显式违规项，却难以判断这些配置在真实场景中是否能够被有效利用。围绕这一问题，Shamim 等\cite{shamim2025prescription}评估了 CIS 推荐配置的合规现状，指出从业人员对安全基线的理解存在明显差异，现有 SAST 工具的检测覆盖也存在不足；其后续工作\cite{shamim2025dastk8s}进一步论证了将 DAST 动态分析纳入配置核验流程的必要性。由此可见，云原生配置安全研究，现有研究更关注配置风险对应的动态攻击路径。

相较于针对单份清单的配置检查，模板与基础设施即代码安全分析更关注风险如何通过依赖关系和复用机制传播。Helm Chart 及其生态是这一方向的典型研究对象。Zerouali 等\cite{Zerouali_2023}和 Blaise 与 Rebecchi\cite{Blaise_2022}分别从生态规模与依存关系角度分析了 Helm Charts 带来的供应链风险，说明安全问题并不总是由单一错误配置导致，也可能通过模板依赖与复用机制在系统中扩散。Ul Haque 等\cite{KGSecConfig2022}进一步提出知识图谱框架 KGSecConfig，对跨平台安全配置概念进行统一抽取与建模，以缓解多平台安全语义碎片化问题。这一方向的研究表明，云原生安全分析已由局部配置项检查逐步扩展到面向模板、依赖链和安全语义的系统化建模。

仅有配置与模板分析仍不足以揭示权限风险如何沿系统结构演化为完整攻击链，因此相关研究进一步聚焦于架构缺陷、过度授权与授权链传播。Dell'Immagine 等\cite{Dell_Immagine_2023}面向微服务部署定义了一组安全反模式并实现自动检测工具 KubeHound，表明权限风险可能嵌入服务交互结构之中。Yang 等\cite{yang2023take}系统分析了 Kubernetes 生态中第三方插件的权限配置，设计了多种攻击路径利用策略，说明节点逃逸、控制面访问与第三方组件权限可以共同演化为全集群接管。Gu 等\cite{gu2024epscan}提出 EPScan，通过面向容器的程序分析自动比对实际资源访问行为与声明权限，识别可被利用的过度特权。与前述配置合规研究相比，这类工作更强调风险如何沿授权链路形成并被放大。不过，其输出大多仍停留在风险发现与报告层面，尚未进一步扩展到围绕具体漏洞生成临时防控策略的研究。

即便控制平面配置与授权链风险得到一定约束，网络和运行时仍是云原生权限安全不可忽视的边界层。Minna 等\cite{Minna_2021}指出，容器编排引入的网络抽象与传统安全模型存在显著差异，这意味着权限提升后的攻击后果可能借助网络路径进一步扩散。Budigiri 等\cite{Budigiri_2021}基于 eBPF 评估了网络策略的性能代价，Kim 等\cite{Kim_2025}对比了多种容器网络接口插件的安全能力，二者共同揭示了网络策略在过滤深度与转发性能之间的权衡。在更具体的缓解机制方面，Pecka 等\cite{pecka2022privilege}通过流水线攻击场景说明“工具合规”并不等同于“系统安全”，KubeFence\cite{cesarano2025kubefence}通过裁剪非必要 API 参数实现了比 RBAC 更细粒度的接口过滤，Zhu 与 Gehrmann\cite{Zhu_2022}以及 Le 等\cite{Le_2023}则分别从 AppArmor 配置自动生成和系统调用感知调度角度强化节点侧防护。这类研究扩展了云原生权限安全的边界，但更多强调通用防护能力，而非围绕具体漏洞构造针对性处置措施。

总体来看，云原生权限安全研究已经从配置合规检查推进到模板依赖分析、授权链挖掘以及运行时隔离的综合治理，形成了比通用系统更强调多层耦合与跨层传播的分析视角。然而，现有研究仍存在三个共同不足：其一，多数工作关注的是风险发现和规则校验，对具体漏洞的利用链分析仍然不足；其二，现有防控手段以通用规则和预定义策略为主，难以在补丁窗口期快速形成面向特定漏洞的临时处置措施；其三，检测、评估与防护往往相互分离，尚未形成由漏洞语义驱动、同时兼顾监控与防护的协同策略生成框架。这些不足构成了引入智能化方法的直接背景。

\subsection{智能化漏洞防控}

智能化漏洞防控研究的关键问题在于：模型是否具备完成安全任务的能力，能否从漏洞信息中生成可用的防控措施，以及能否借助多智能体协作处理多阶段、高反馈依赖的复杂安全任务。围绕这一问题，现有研究大体可归纳为三个层次：大语言模型安全任务评测、模型驱动的漏洞理解与规则生成，以及多智能体驱动的安全任务自动化。

大语言模型安全任务评测研究首先回答“模型能否用于安全任务”这一基础问题。Chang 等\cite{chang2024survey}系统综述了 LLM 通用评测方法与基准设计原则，为安全领域的专项评测提供了方法参照。在此基础上，安全领域的评测工作逐渐从通用能力测试转向面向真实安全任务的专门基准。Yin 等\cite{yin2024multitask}围绕漏洞检测、定位与修复等多个软件漏洞子任务对主流 LLM 进行测评，结果表明当前模型在漏洞定位与跨语言理解方面仍存在明显短板。Fu 等\cite{fu2025raseval}将评测对象进一步扩展到 LLM 智能体，提出面向真实安全运维环境的评测框架，以考察智能体在信息不完整与噪声干扰条件下的稳定性与鲁棒性。Zhang 等\cite{zhang2025defenderbench}则构建了覆盖告警研判、威胁检测与安全响应等多类防御任务的语言智能体评测基准 DefenderBench，为不同模型和智能体框架之间的横向比较提供了统一平台。上述工作表明，若缺乏面向真实安全任务的系统化评测，模型能力便难以被可靠比较，更难支撑其在漏洞防控场景中的实际应用。

在明确模型能力边界之后，研究进一步转向“模型能否理解漏洞并生成防控措施”这一问题。围绕漏洞语义理解，Ghosh 等\cite{ghosh2025cve}提出以安全领域本体辅助 LLM 完成 CVE 漏洞评估，通过引入漏洞类型、攻击向量和影响范围等结构化知识约束模型推理，提升了漏洞语义理解与风险评估的准确性。在云原生误配置修复方向，Malul 等\cite{malul2024genkubesec}提出 GenKubeSec，将 LLM 引入 Kubernetes 误配置的检测、定位、推理与修复建议生成，构建了面向云原生配置安全的全流程自动化处理框架；Minna 等\cite{minna2025analyzing}进一步评估了 LLM 修复 Helm Chart 配置异味的效果，指出仅以局部 YAML 片段为输入往往难以生成完整修复方案，且模型存在误删无关配置的风险，说明上下文完整性与输出可靠性是当前方法的关键约束。除修复建议之外，LLM 也开始被用于检测规则生成。Konstantaras 等\cite{konstantaras2026edrrules}探索了由模型从威胁描述中自动归纳生成终端检测与响应规则的方法，为将自然语言形式的攻击知识转化为可部署规则提供了初步路径。总体而言，这类研究展示了从漏洞描述到防控措施生成的自动化潜力，但已有工作多聚焦于通用误配置或孤立漏洞场景，输出也多停留在修复建议或单条规则层面，尚未形成面向云原生权限提升漏洞的多策略协同生成与部署验证闭环。

当安全任务具有多阶段依赖、高上下文需求和反馈迭代特征时，单一模型往往难以稳定完成整条任务链条，因此多智能体驱动的安全任务自动化成为新的研究方向。Alsabbagh 等\cite{alsabbagh2026autosecagent}提出 AutoSecAgent，通过智能体编排、递归记忆与检索增强生成，使系统能够在多步骤安全任务中跨轮次积累上下文并稳定执行，从而缓解单模型在长链路任务中的信息遗忘问题。Yang 等\cite{yang2026autoegexploitingknownthirdparty}则针对云原生生态中已知第三方组件漏洞的利用验证问题，设计了多智能体协同与迭代反馈机制，通过多轮自主探索实现从漏洞信息到可验证利用策略的端到端自动化。上述研究说明，多智能体框架已在渗透测试和漏洞利用生成等攻击侧任务中显示出较强潜力。然而，现有工作主要集中于漏洞发现与利用验证，在防御侧的策略生成、评审优化与部署验证方面仍缺乏系统性框架，尤其尚未回答如何围绕具体权限提升漏洞自动生成兼顾防护与监控的策略代码，并通过评审与实验完成质量控制。这一空白构成了本文在智能体工作流设计层面的直接切入点。

\subsection{前期工作}

在前述研究基础上，课题组围绕 Kubernetes 权限风险检测已形成较为系统的前期积累，其中代表性成果为 KubeGuard 框架。该框架面向过度权限、权限提升和敏感信息泄露三类风险，分别设计了最小权限集构建、规则化审计以及敏感词监测机制\cite{kubeguard_icws2025}。如图\ref{fig:kgf}所示，KubeGuard 由过度权限检测、权限提升检测和敏感信息泄露检测三个模块构成。

KubeGuard 的核心贡献在于验证了从权限视角开展风险建模与检测的可行性。一方面，该工作利用 NLP 技术识别应用所需的最小权限集，以判断权限配置是否存在过度授权；另一方面，通过动态规则审计识别多类权限提升风险。具体而言，该框架将权限提升场景归纳为凭证窃取、账户冒用、RBAC 操纵和间接执行四类，并分别提出相应的检测思路。此外，系统还通过监测 Pod 间消息传输并结合关键词匹配，对涉及敏感资源的内容进行告警，以覆盖敏感信息泄露风险。在系统实现与效果验证方面，课题组进一步实现了原型系统 KubeGuarder，并在开源 Kubernetes 应用与模拟场景中开展实验评估\cite{kubeguard_icws2025}。实验结果表明，该系统在过度权限检测方面较静态基线方法具有更高的有效性与准确性，同时能够识别多类型权限提升与敏感信息泄露风险。

尽管如此，现有前期工作仍主要停留在权限层面的规则化检测，其核心依据仍是 RBAC 配置与 API 访问行为之间的匹配关系。这一路径在真实生产环境中至少存在三方面局限：其一，仅依据权限配置与操作行为之间的对应关系，难以准确区分正常运维行为与恶意提权行为，误报风险较高；其二，该方法主要面向控制平面与资源访问层，尚未深入节点侧系统层面的权限提升漏洞，对容器逃逸、SUID 配置不当及内核漏洞等底层利用缺乏针对性检测能力；其三，基于预定义规则的检测方式对未知漏洞和新型攻击手法的泛化能力有限。换言之，前期工作已经证明了“从权限视角发现风险”是可行的，但尚未解决“如何围绕具体漏洞构建兼顾检测、监控与防护的智能化临时处置策略”这一更进一步的问题。本文的研究正是在这一基础上展开，即在继承权限视角优势的同时，引入漏洞知识组织、策略代码生成、评审优化与部署验证等机制，形成面向云原生权限提升漏洞的智能化防控框架。

\section{小结}

本章围绕本文所关注的云原生权限提升漏洞智能化防控问题，介绍了容器、Kubernetes 及其权限模型等基础概念与云原生安全技术，并从权限提升风险与防控、云原生权限安全以及智能化漏洞防控三个方向梳理了国内外研究现状。结合课题组前期工作的成果与局限，可以看出，现有研究虽然分别在权限风险分析、云原生安全治理和智能化安全任务求解方面取得了进展，但仍缺乏面向具体云原生权限提升漏洞、能够贯通漏洞知识组织、策略生成、质量评审与部署验证的统一方法框架。本文的研究定位正是填补这一空白，并为后续方法设计与实验验证奠定理论基础。
