\section{背景与意义}

服务计算的发展推动了服务软件的大规模部署\cite{bouguettaya2017service}。在服务计算场景下，软件体系结构经历了从单体架构向面向服务架构(SOA)的转变，并进一步发展至微服务架构\cite{zhong2024ddd}。微服务系统由多个可独立开发、部署和演化的微服务组成，可分布式部署到多个计算节点。云原生技术将微服务和云计算结合，实现微服务系统在大规模计算集群中的弹性扩缩、持续交付和高可用运行\cite{cncf2024definition,cncfwhoweare}。

云原生技术离不开容器集群基础设施的发展。容器技术依托内核级隔离和镜像分发成为微服务高效封装与运行的单元\cite{wuyiwen2023docker}，但不能满足多节点资源调度和自动编排等需求。谷歌公司开发了容器管理系统 Borg\cite{Verma_2015}，并以此为参考在 2014 年开源容器集群编排系统 Kubernetes（简称 K8s），后捐赠给云原生基金会 CNCF\cite{lawson2026cncf} 管理。K8s 通过主从式集群架构与声明式 API 实现对容器资源与应用状态的分布式管理，成为重要的云原生基础设施。

K8s 集群的运行维护通常依赖多类第三方云原生应用。为实现日志采集、监控告警和身份认证等能力，系统管理方会引入 Fluentd、Prometheus、Keycloak 等开源应用。这些应用能够增强平台能力并降低开发运维成本，但其组件深度参与集群运行与控制过程，也会给 K8s 集群引入相应的第三方安全风险。其中，\textbf{权限安全风险是容器集群基础设施的重要风险来源}。云原生应用通过 RBAC 机制\cite{ferraiolo1995role}获取一定的集群访问权限，若应用组件存在过度授权\cite{gu2024epscan}、授权检查缺陷、敏感信息泄露\cite{kubeguard_icws2025}或网络隔离配置不当等安全漏洞，攻击者可借此实施权限提升攻击，严重时甚至可接管整个集群\cite{yang2023take}。相关漏洞可称为\textbf{云原生应用的权限提升漏洞}。

云原生应用的权限提升漏洞管理面临三方面问题：

\noindent\hangindent=2em\hangafter=1 (1)\textbf{修复时间不确定性}。不同开源社区安全响应能力参差不齐，漏洞从公开披露到补丁发布的周期因项目而异且难以预期。2020 至 2025 年间 55 个云原生权限提升漏洞的修复时间分布如图\ref{fig:patch-window}所示，其中 $30.4\%$ 的漏洞补丁修复存在滞后问题，攻击者可借助公开公告与修复提交发现漏洞利用条件。此外，第三方组件升级受限于现有架构兼容性和业务连续性要求，导致补丁无法立即部署到生产环境。

\noindent\hangindent=2em\hangafter=1 (2)\textbf{现有安全工具对具体漏洞的监控与防护能力不足}。现有技术和研究通常通过配置扫描\cite{shamim2025prescription,k8smanifests2023}、运行时检测\cite{falco2025}、准入控制\cite{opa2025,kyverno2025}和网络隔离\cite{Minna_2021,Budigiri_2021}等方式应对安全风险。其中，运行时检测用于在集群运行过程中发现异常行为，准入控制用于在资源写入集群前执行策略校验，网络隔离用于限制 Pod、服务或命名空间之间的通信范围。这些工具能够提供基础安全能力，但监控与防护逻辑多面向通用风险，并非针对具体漏洞定制，对特定高危 CVE 的实际拦截效果有限；部分工具还需要使用领域特定语言手工编写安全策略，策略编写成本较高。

\noindent\hangindent=2em\hangafter=1 (3)\textbf{补丁窗口期处置依赖专家经验}。云原生权限提升漏洞通常跨越 RBAC 授权\cite{ferraiolo1995role}、控制平面交互、网络隔离和应用行为等多个层面，涉及过度授权\cite{yang2023take}、风险组件劫持、敏感信息泄露\cite{kubeguard_icws2025}等问题，补丁窗口期的处置高度依赖安全专家经验，难以快速形成可部署的安全策略。

大语言模型的发展为高危漏洞的智能化治理提供了新的技术路径。仅依赖通用规则或人工经验，难以在补丁窗口期内为具体漏洞快速形成缓解措施。大语言模型不能直接替代准入控制、运行时监控等安全工具，但能够通过漏洞理解与复杂推理生成面向这些工具的领域特定策略代码，为漏洞处置提供自动化支持。将大语言模型用于云原生权限提升漏洞监控与防护，还需解决以下三个核心问题：

\noindent\hangindent=2em\hangafter=1 (1)\textbf{如何构建面向具体漏洞的安全上下文}。权限提升漏洞相关的漏洞成因、利用条件与影响边界等关键信息分散在代码仓库、问题讨论区与修复提交等多类来源中，需要建立可检索、可追溯的领域安全知识库，将分散证据组织为可供大语言模型使用的安全上下文。

\noindent\hangindent=2em\hangafter=1 (2)\textbf{如何基于漏洞语义生成安全策略代码}。大语言模型的单步问答难以稳定完成从漏洞理解到策略构造的全过程。策略代码生成关联漏洞成因分析、攻击路径识别、安全工具选择等细节问题，需要通过完整工作流加以组织与约束。

\noindent\hangindent=2em\hangafter=1 (3)\textbf{如何评估安全策略代码质量}。模型幻觉问题可导致安全策略代码覆盖不足、干扰业务或配置不完整等多方面问题。策略代码的测试预言\cite{oracleproblem2015survey}构建与结果判定成本过高，实际评估需通过人工复现漏洞并模拟攻击验证代码质量。

围绕上述问题，本文提出基于大语言模型的智能化安全策略生成方法 KPEDefense，并开发相应的支持工具；以近 5 年云原生权限提升漏洞为实验对象，对方法的监控与防护效果进行系统评估。

\section{研究内容与成果}
本文面向云原生应用权限提升漏洞的智能化监控与防护需求，结合漏洞描述与开源仓库信息，基于大语言模型生成可用于动态监控与防护的安全策略，从而降低漏洞披露后第三方组件带来的安全风险。主要研究内容与成果如下。

\textbf{(1)提出一种智能化安全策略生成方法}。本文提出面向权限提升漏洞监控与防护的智能化安全策略生成方法KPEDefense。该方法系统归纳历史权限提升漏洞的成因，提出权限提升漏洞分类框架，并基于开源仓库中的多源漏洞信息构建安全知识库；在此基础上，通过多智能体协同工作流生成针对具体权限提升漏洞的策略代码，并从有效性、无干扰性与可部署性三个维度构建多源模型评估体系，以保障策略代码质量。

\textbf{(2)开发支持工具}。本文开发 KPEDefense 方法支持工具，集成权限提升漏洞知识库管理、策略生成工作流、专家评审排序与策略部署验证等功能，实现面向云原生权限提升漏洞的智能化监控与防护。

\textbf{(3)实验评估}。以近 5 年云原生权限提升漏洞样本为实验对象，从质量与效率两个方面评估 KPEDefense 生成的安全策略。实验结果表明，KPEDefense 能够针对真实云原生权限提升漏洞生成有效的监控与防护方案，且时间与经济成本开销较低。
