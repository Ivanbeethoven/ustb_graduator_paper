
\chapter{面向云原生权限提升漏洞的智能化防控系统设计与实现}\label{chap:system}

本章在第三章方法基础上实现 KPEAgent 原型系统。系统不将检索、推理和反馈视为彼此割裂的功能点，而是围绕第三章提出的“安全上下文构建、结构化漏洞分析、候选策略生成、评审反馈优化与质量排序确认”这一方法链条进行工程化落地，形成覆盖漏洞知识管理、会话驱动生成、专家评审和策略交付的完整闭环。下文从需求分析、总体设计和详细设计三个层面展开说明。

\section{需求分析}

\subsection{用户角色与用例分析}

系统围绕\textbf{安全工程师}与\textbf{专家评审员}两类角色组织核心用例，见图~\ref{fig:role_use_case}。安全工程师负责选择漏洞实例、发起分析会话、查看证据与候选策略，并完成部署与验证；专家评审员负责对同类型候选策略进行三维质量评审、排序确认与反馈修订。两类角色共同服务于第三章所定义的候选策略集合 $\Pi_v$ 的生成、优化与最终交付。

    \bicaption{系统用户角色与核心用例（UML 用例图）}{System user roles and core .use cases (UML use case diagram)}

\subsection{功能需求}

结合两类角色的职责以及第三章的方法链条，系统需要具备以下五项核心能力：

\noindent\hangindent=2em\hangafter=1 (1) \textbf{漏洞知识与证据管理}：导入、检索与维护 CVE 条目及其关联证据，为后续构建安全上下文 $c$ 提供可追溯材料。

\noindent\hangindent=2em\hangafter=1 (2) \textbf{安全上下文构建与候选策略生成}：围绕漏洞实例组织候选证据、形成结构化分析，并输出同类型候选策略集合。

\noindent\hangindent=2em\hangafter=1 (3) \textbf{评审反馈驱动优化}：接收专家评审意见，对候选策略进行修订、补全与再生成，以降低噪声并提升可部署性。

\noindent\hangindent=2em\hangafter=1 (4) \textbf{三维质量评审与排序确认}：围绕有效性、无干扰性和可部署性对同类型候选进行排序比较，并形成可审计的确认结果。

\noindent\hangindent=2em\hangafter=1 (5) \textbf{策略交付与部署验证}：将通过确认的候选策略下发至目标环境，并记录执行状态、验证结果与审计信息。

\section{总体设计}

\subsection{系统架构设计}

系统采用分层架构，自顶向下分为界面层、服务层、智能引擎层和数据层，见图~\ref{fig:system_architecture}。该分层并不是对方法步骤的简单堆叠，而是将第三章中的知识组织、分析生成、评审优化与结果交付拆解为具有明确职责边界的实现单元：

\noindent\hangindent=2em\hangafter=1 (1) \textbf{界面层}：基于 Vue3 构建单页应用（SPA），采用 Pinia 管理应用级状态，并集成 ECharts 可视化组件，负责 CVE 详情展示、策略交互与评审结果呈现。

\noindent\hangindent=2em\hangafter=1 (2) \textbf{服务层}：采用 Flask 实现 REST API 网关，负责请求路由、访问控制与接口编排；同时通过任务调度器（Scheduler）管理耗时较长的会话任务，并协调知识检索、候选策略生成、评审提交与部署验证等流程。

\noindent\hangindent=2em\hangafter=1 (3) \textbf{智能引擎层}：封装系统核心分析能力，由 KPEAgent 引擎统一调度安全知识整理、漏洞分析、候选策略生成、评审反馈吸收与策略优化等处理单元，完成从漏洞实例到候选策略集合的迭代生成。

\noindent\hangindent=2em\hangafter=1 (4) \textbf{数据层}：负责数据持久化与检索支撑，包括存放 CVE 元数据、证据片段、中间分析结果与候选策略对象的文件存储，以及支持安全上下文构建的向量索引库。

\subsection{数据模型设计}

系统的数据持久化围绕四类核心实体展开，见图~\ref{fig:storage_schema}。这些实体与第三章中的漏洞实例 $v$、安全上下文 $c$、候选策略集合 $\Pi_v$ 及其评审结果一一对应；图中按照 UML 标准标注了可见性修饰符（\texttt{-} 表示私有属性，\texttt{+} 表示公有操作）、多重性约束与关联方向：

\noindent\hangindent=2em\hangafter=1 (1) \textbf{CVE 实体}：作为数据源头，包含 \texttt{cve\_id}、\texttt{summary}、\texttt{cvss\_score} 和 \texttt{severity} 等基础属性，并以枚举类型 \texttt{status} 标记当前处置状态（未处理、分析中、已部署）。每个 CVE 与后续生成的会话呈一对多关系。

\noindent\hangindent=2em\hangafter=1 (2) \textbf{会话实体（Session）}：表示一次完整的分析会话，记录所选模型 \texttt{model\_name}、提示词模板 \texttt{prompt\_template} 与会话状态。会话既承载候选证据组织过程，也承载候选策略生成与优化过程，因此与策略呈一对多关系，支持同一漏洞任务下的多版本迭代。

\noindent\hangindent=2em\hangafter=1 (3) \textbf{策略实体（Strategy）}：记录单次生成的完整策略结果，包括策略内容 \texttt{content}、中间分析快照 \texttt{reasoning\_chain}、证据召回片段 \texttt{rag\_snippets} 以及版本号 \texttt{version}，用于支撑候选策略的来源追溯、版本对比和增量追踪。

\noindent\hangindent=2em\hangafter=1 (4) \textbf{排序实体（Ranking）}：存储专家决策结果，其核心属性包括专家评审员标识、决策时间戳、策略排序结果以及多维评分信息。该实体同时关联会话与策略，用于刻画专家对特定候选策略集的即时评价。

\subsection{数据流转与处置流程设计}

为保证关键决策可追溯，系统构建了图~\ref{fig:data_flow_audit} 所示的闭环数据流。与第三章方法定义一致，该流程不再将系统简单理解为“检索后生成”的单段链路，而是拆解为安全上下文构建、漏洞分析与候选策略生成、评审反馈与策略优化、质量排序与结果确认，以及最终的审计归档五个环节。漏洞实例首先与候选证据共同进入上下文构建阶段，形成带来源标识的安全上下文；随后系统围绕该上下文输出候选策略集合及其中间分析结果；专家评审意见继续驱动候选修订与结果确认，最终将排序结果和审计记录写入持久层，形成可复核的处置证据链。

\section{详细设计与实现}

本节按功能模块说明系统的交互流程与实现方式。各模块遵循前述分层架构与数据模型约束，并围绕 CVE 处置生命周期中的关键状态迁移展开。下文依次介绍知识库管理、策略生成与优化、专家评审与排序以及策略部署管理四个模块。

\subsection{CVE 知识库管理}

知识库管理模块承担漏洞条目的汇聚、检索、证据关联与状态维护，是安全上下文构建的入口环节。该模块对应服务层的 CVE 知识库组件，直接影响 CVE 实体的 \texttt{status} 字段及后续会话流程。如图~\ref{fig:ui_cve_list} 所示，系统主界面以列表视图展示已录入的 CVE 条目，核心字段包括 CVE 编号、漏洞摘要、CVSS 风险评分和当前处置状态。界面上方提供关键词检索与状态筛选功能，支持安全工程师依据漏洞编号、漏洞类型或关键描述快速定位目标记录；选择具体条目后，系统即可进入详情视图并发起分析会话，为后续候选证据检索和安全上下文整理提供统一入口。

\subsection{策略生成与优化}

策略生成与优化模块负责将漏洞证据转化为可交付的候选策略，并通过评审反馈闭环持续修订结果。该模块由 KPEAgent 核心引擎及其处理单元组成，并由服务层的策略生成组件和任务调度器协同驱动。系统以会话（Session）为基本单元，维护单个漏洞分析任务的上下文与执行状态，避免不同漏洞之间相互干扰。

\subsection{专家评审与排序}

专家评审与排序模块负责将候选策略转化为可用于决策和模型对齐的偏好数据。该模块接收策略生成模块输出的同类型候选策略集合，并输出满足排序实体（Ranking）结构约束的结果。系统通过“三维质量评审 + 同类型排序确认”两个阶段引入专家知识，并为后续模型对齐提供偏好信号。

评审阶段侧重采集细粒度定性反馈。如图~\ref{fig:ui_review_detail} 所示，结构化评审详情页要求专家评审员围绕有效性、潜在干扰风险和实施前置条件等因素对候选策略进行逐项核查，并允许输入自由文本意见。这些反馈可作为策略优化与再生成的重要依据。

\begin{figure}[htb]
    \centering
    \includegraphics[width=0.85\textwidth,height=0.38\textheight,keepaspectratio]{images/ui/review详情}
    \bicaption{评审阶段的结构化输出示例}{Example of structured output in the review stage}
    \label{fig:ui_review_detail}
\end{figure}

排序阶段侧重同类型多候选方案之间的相对比较与一致性判别。如图~\ref{fig:ui_ranking} 所示，拖拽式排序主界面左侧列出同一 CVE 的多个候选策略，右侧设置有效性、可部署性与无干扰性等维度评价区，并提供必要的排序提示。相较于绝对打分，拖拽排序更有利于控制评分尺度漂移；维度评价区则为排序结果提供解释依据。系统以排序结果作为主信号，以维度判断和文本备注作为辅助信号，形成后续一致性分析与模型对齐所需的偏好样本。

为支持细粒度比较，系统允许专家评审员展开单个候选策略的详细信息。如图~\ref{fig:ui_ranking_detail} 所示，专家评审员可在该界面对不同方案的规则逻辑、关键参数与实现细节进行逐项核对，重点关注策略对攻击路径与权限边界的覆盖范围、规则前置条件与约束是否充分且不过度收紧，以及执行代价与潜在业务影响是否可接受。这种呈现方式减少了因信息分散造成的判断偏差，并提高了排序决策的稳定性。

\subsection{策略部署管理}

策略部署管理模块负责将通过评审的候选策略下发至目标环境，并在 CVE 处置生命周期中完成从已批准到已部署的状态迁移。如图~\ref{fig:ui_deploy_config} 所示，部署目标配置界面为 Kubernetes 集群和传统主机环境提供两类配置方式。对于 Kubernetes 集群，系统通过 Python Kubernetes SDK 与 API Server 建立连接，安全工程师需配置集群地址、访问令牌与命名空间；对于传统主机环境，系统支持基于 SSH 的部署方式，需要输入主机地址、端口和认证密钥。正式部署前，系统提供连通性测试。
